# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diff stays inside the plan | The diff's changed files, each read against the plan's stated scope (the files and folders it names, the changelog entry it promises) and its deviation notes | Every changed file is named by the plan (the file or its folder), is the changelog entry the plan promises, or is covered by a deviation note that explains it. A changed file the plan never names and no note covers is a fail, even if the hunk looks harmless | required |
| Nothing the plan promised is missing | The plan's scope list and test plan, read against the diff | Every file, behavior, and test the plan commits to is in the diff, or a deviation note says it was dropped and why. A silently dropped item is a fail; an honestly disclosed shortfall passes | required |
| Description claims match the diff | Each fidelity claim in the description ("implements the plan exactly", "no changes beyond it", "no options added"), read against the diff | Every claim is true of the diff. A claim of exact fidelity fails if either check above failed. A claim that something wasn't added passes if nothing in the diff adds it | required |
| Checklist claims have proof | Each checked-off item in the description's checklist (a test for X, a changelog entry, docs), read against the diff | For each item, the diff contains the thing claimed: a test file or case that exercises X, the named changelog file, and so on. One checked item with nothing behind it is a fail | required |
| Tests cover the plan's test plan | The plan's test plan (the issue's input, each named failure mode, the control, each edge case), read against the diff's test files and the test-evidence section | Every case in the plan's test plan is exercised either by a test in the diff or by a re-run shown in the test evidence, or a deviation note drops it with a reason. A named case or failure mode with neither a test nor a shown re-run is a fail | required |
| Test evidence is observable | The test-evidence section, read against the plan's repro and its expected-after behavior | The plan's own repro (the failing input, not a control or an unchanged path) is re-run on the branch, and the evidence names a concrete observed before and after: printed output, an error message, an exit code, or a specific described result such as "toast appears, file still listed". A before/after transcript counts even when annotated with comments. Bare assertions ("tested locally", "colors work now", "works on my machine") and evidence that only exercises the unchanged path fail | required |
| Repo's own checks were run | The test-evidence section, read against the checks the repo or the plan's test plan names (CONTRIBUTING, PR template, CI config, the plan's "run X") | The test suite and any command the plan's test plan names are stated with their specific command and outcome (for example "`pytest tests/ -q` passes (1462 passed)" or "`go test ./...` passes"). Formatting, lint, and regenerate-type checks the repo's template lists count when the description attests them in its requirements list (for example "code formatted; cheatsheets regenerated, no diff"). Or the description says honestly which weren't run and why. Output dumps are not required. A bare "tests pass" or "all tests pass" with no command named, or a required check never mentioned, fails | required |
| Diff is reviewable | The diff and the commit list | No debug leftovers (stray logs, commented-out code), no dead code, no formatting churn, and no unrelated drive-by hunks. Judge by what's in the diff, not its length: a large diff where every hunk serves the plan passes | required |
| Standards: template filled | The repo-facts block's PR template sections, read against the description | Every template section has real content for this change, or "n/a" with a reason where it truly doesn't apply. Boilerplate left as-is or a skipped section is a fail. If the repo has no template, this passes | required |
| Standards: AI-use disclosure | The repo-facts block's stated AI policy (the contribution policy line), read against the description | Treat every package as AI-assisted work. If the policy requires AI-use disclosure, the description itself must contain a disclosure sentence (the tool used and the extent of assistance, if the policy asks for that). A description with no such sentence fails, even when the fix is excellent. If the policy says nothing about AI or is "no stated AI policy", this passes | required |
| Standards: stated policy honored | The repo-facts block's other contributing instructions and stated policy (one PR per issue, branch naming, CLA, restrictions on private APIs, maintainer direction in the thread), read against the PR | Each stated ask is visibly honored, and explicit maintainer direction in the thread is engaged with, not ignored | required |
| Title and description say what the diff does | The PR title and description, read against the diff | A maintainer could learn from the title what the change does, and the description names the actual behavior change. Judge accuracy and substance, not length or polish | preferred |

## Verdict rule

Accept if every `required` check passes. Reject if any `required` check fails. `unclear` counts as `fail`: a claim you can't verify from the package isn't ready to submit. `preferred` checks get reported but never change the verdict. A PR that honestly discloses a shortfall (a deviation note, a stated untested case, a check not run with a reason) passes the check that shortfall touches. Hold a PR for gaps it hides, not for ones it discloses.

When more than one required check fails, the deciding check is the first failing required check in the table's order.
